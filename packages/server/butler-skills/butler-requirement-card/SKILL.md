---

## 何时用
主人要新建需求、把一段对话整理成需求卡，或主人提供了 PRD / 后端设计文档 /
接口文档 / 前端设计稿 / Figma 等链接要归到某个需求下时（文档内容不由管家
生成——主人给链接，链接作为上下文归档到需求卡）。

## 工作流
1. 先抓标题：一句话，动词开头，可验证。
2. 按六段写正文；不知道的写「待补充」，不要编。
3. 收集上下文：主人提供的文档一律以链接归档——PRD / 后端设计文档 / 接口文档 /
   前端设计稿 / Figma 等，每条给 { kind: link, name, ref }（name 写文档名，如
   「后端设计文档」「Figma 首页稿」）；聊天附件在 files/ 下，给 { kind: file, name, path }。
   卡片建好之后再到的文档链接，引导主人在工坊需求卡的「上下文」里自行添加。
4. 把来源线程 thread 和触发事件 event_id 带上。
5. 用 create-requirement 调用动作通道（地址见 action.json）；主人说清了项目就带 project_id，否则批准时主人在审批卡里选。每次新生成 idempotency_key，重试复用同一个。
6. 返回 pending_approval 时，告诉主人「已送到管家页的审批」，等结果事件；不要称建好了。

## 六段模板

## 背景 / 为什么

（待补充：现状、问题、为什么现在做。）

## 目标

（待补充：可验证的结果。）

## 范围

（待补充：做什么、不做什么。）

## 约束

（待补充：技术、时间、兼容性，不能动的东西。）

## 验收

（待补充：可以检查的通过条件。）

## 开放问题

（待补充：需要主人拍板的点；不知道就先写待补充。）

## 每段写什么

1. ## 背景 / 为什么 —— 现状、问题、为什么现在做。
2. ## 目标 —— 可验证的结果。
3. ## 范围 —— 做什么、不做什么。
4. ## 约束 —— 技术、时间、兼容性，不能动的东西。
5. ## 验收 —— 可以检查的通过条件。
6. ## 开放问题 —— 需要主人拍板的点；不知道就先写待补充。

## 注意
- 需求卡是一份 Markdown 文档，不要把内容拆成问答。
- 文件只给路径；批准后会复制进需求自己的文件夹。
- 正文最多 20000 字；一个需求一张卡。
