让管家动手，
先给一张合格的卡。

管家要能建需求卡，但不是“点一下就多一张卡”。这一版把三件事连起来： 授权开关决定要不要人点头，管家页里的审批让人一次看清所有待批， 一张 Markdown 需求卡保证批准的那份文档带着背景、目标、验收和上下文。

审批在管家页 审批开关 需求卡 = Markdown 上下文随卡 待拍板
01

问题不在“能不能建”，在“建出来是什么”

现在的管家能聊、能看台账；M2 给了它建卡和派活的手，但没有让人看清、改动的入口。

现状 · Today

能建，但很黑

  • 授权在对话里问一次，主人可能不在；授权结果只落一个偏好文件，看不见。
  • 审查入口散落在聊天里，没有“所有待批”一栏。
  • 需求卡只有标题和一个自由文本；正文没有编辑器，主人看不到管家写了什么。
  • 上下文是单独的链接/文件列表；建卡时不能随卡一起交给管家。
  • “卡”没有固定格式，管家每次写的结构都不一样。
→
目标 · This design

能建，而且看得见、改得动

  • 开关：建卡 / 派活 / 停止，各自“每次审批”或“直接允许”。
  • 审批在管家页里：和对话同一个地方，页签「对话 / 审批」，不用再开一个页面。
  • 文档：需求卡就是一份 Markdown 文档，固定六段 + 上下文小节，主人可读可改。
  • 上下文随卡：链接与文件一并进卡；文件复制进需求自己的文件夹。
  • 结果回流：批准/拒绝都变成事件唤醒管家，它再向主人汇报。
一份文档，一个来源：需求卡就是 notes + contexts 渲染出的 Markdown 文档； 审批、工坊、会话开场读的是同一份，不是三份摘要。

从主人开口，到卡进入需求、会话开跑、结果回到管家。开关只改一件事：中间要不要经过管家页的审批页签。

为什么审批卡要放完整卡片

key choice

只给一句“管家想建卡”等于让人盲签。审批卡里直接渲染将要进入需求的那张 Markdown 卡和上下文清单，主人批准的是内容，不是动作。第一版只读预览；批准后到工坊再改。

为什么结果还要回给管家

closing loop

批准后建卡是守护进程做的，不是管家“假装做了”。它需要一条butler.action.approved事件，才能如实说“卡建好了”；拒绝同理。没有这条回流，审批页签就只是另一块没人收尾的表单。

03

需求卡：一份有固定骨架的 Markdown

它是一份 Markdown 文档，不是一张表单：标题一句话，正文六段，上下文单独列；启动会话时原样成为会话的开场白。

登录页改版
需求 ID · req_01J8…　阶段：需求设计　优先级：中
来源：与主人的对话 · msg_01J…

背景 / 为什么

登录页是转化入口，现在的首屏要 3 秒才出来，移动端还会错位。本月先把结构重排，视觉不变。

目标

- 首屏在 1 秒内可交互 - 移动端不再横向滚动 - 登录成功率不低于现在

范围

做：布局、加载顺序、断点 不做：重做视觉、改后端鉴权、加第三方登录

约束

- 保持现有设计令牌 - 不能引入新的运行时依赖 - 上线前要过现有回归

验收

- [ ] 桌面 / 移动端都不横向滚动 - [ ] 首屏交互 ≤ 1s（本机与低端机各测一次） - [ ] 登录走通一条真实账号

开放问题

- 低端机的具体机型？ - 是否需要保留旧版入口？

数据模型：卡不是副本

          
三份数据各管一件事：需求记录是事实，审批记录是待办，偏好文件是开关。卡片是需求记录的渲染。

        

      


      

        

          Requirement · 事实
          
需求记录

          
    
            
  • title 一句话标题
    • 
            
  • notes 卡片文档正文（Markdown，六段）
    • 
            
  • contexts[] 文档的上下文小节（链接 / 文件）
    • 
            
  • threads[] 来源与执行线程
    • 
            
  • stage / priority 生命周期
    • 
          

        

        

          Approval · 待办
          
审批记录

          
    
            
  • id apr_…
    • 
            
  • action create / launch / stop
    • 
            
  • status pending / approved / denied / failed
    • 
            
  • detail 给主人看的文档预览
    • 
            
  • payload 执行用的动作体，只在服务端
    • 
            
  • idempotency_key 重试不重复
    •

管家技能：butler-requirement-card

          
建卡不是自由发挥，而是一套固定的整理流程。它是独立技能，butler-intake 负责在入口接住主人。

把一段对话整理成一份需求卡文档

            
产出：一份 Markdown 文档（card.md）+ 一组上下文引用。目标是在不啰嗦的前提下，把主人已经说过的信息收进固定六段；缺的标“待补充”，不编。

    3.

    4.

    5.

分期与待拍板

          
先把“合格的卡 + 审批回路”做成一条可用的线，再扩到派活/停止和工坊编辑。

        

      


      

        已定前提（你）：审批放在管家页的「对话 / 审批」页签里，不做独立页面；
        需求卡是一份 Markdown 文档，正文与上下文是同一份文档，不是一张需要另存副本的表单。
      


      

        

          Phase 1 · 先做
          
卡片 + 审批闭环

          
    
            
  • 共享卡片格式：六段模板、渲染器、缺段检查。
    • 
            
  • butler-requirement-card 技能 + 人设/入口技能接线。
    • 
            
  • create-requirement 支持正文、链接、文件、来源线程。
    • 
            
  • 审批记录 + 开关 + 管家页「审批」页签 + 完整文档预览 + 批准后执行 + 结果事件。
    • 
            
  • 工坊的需求卡编辑器（至少能读、能改正文）。
    • 
          

          验收：说“建卡” → 管家页的审批页签出现完整文档 → 批准 → 文档/上下文/线程落地 → 管家收到结果。
        

        

          Phase 2 · 接着
          
把其它审批也收进来

          
    
            
  • 派活 / 停止改用同一审批模块（替换对话里的 L3 问法）。
    • 
            
  • “以后直接允许”写入开关；可查看、可撤销。
    • 
            
  • 把现有 agent 权限请求聚合进管家页的审批页签：先只读跳转，再就地回答。
    • 
            
  • 工坊需求卡文档补全、上下文预览、导出 card.md。
    • 
          

          验收：所有需要人的动作都只在管家页的审批页签出现一次；开关能单独控制每类动作。
        

      


      

        

          
Decision 1 · card document需求卡文档的正文用现有 notes，还是新增 card 字段？

          
建议：notes 作为文档正文，不新增字段，避免两套真相；旧的无标题 notes 兼容包在「背景」下。

        

        

          
Decision 2 · files上下文文件复制进需求文件夹，还是只记路径？

          
建议：复制到 requirements/contexts/<req>/，管家文件夹清理后卡不坏。

        

        

          
Decision 3 · skill建卡技能独立，还是扩展现有 butler-intake？

          
建议：独立 butler-requirement-card；intake 只负责入口和追问，职责清楚。

        

        

          
Decision 4 · approval preview审批里的文档只读，还是批准前可编辑？

          
建议：第一版只读；批准后到工坊编辑。可编辑会把审批页签变成另一个编辑器，风险大。

        

      


      

        测试要点：模板渲染/缺段、动作带上下文（链接校验、文件复制）、审批 pending → 批准建卡 → 拒绝不建、开关 ask/auto、幂等、窗口专属决策、
        结果事件唤醒管家；外加一次“干净房间”测试：只给管家这份技能，在临时目录里完成一张真实需求卡。
      


      

        
给管家的不是“建卡权限”，
而是一条看得见、改得动、能收尾的路。
