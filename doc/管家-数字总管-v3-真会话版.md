# 设计：管家——真会话版（v3，取代一期的大脑与对话通道）

> 需求：req_01M83533QKG0KJE5MXXDT4AKWS「优化 工坊 对接 opencode 场景」的管家方向。
> 2026-11-25 按 owner 方向调整撰写：**管家的大脑从「模型直连」升级为「终端级真会话」**，
> 页面就是和这个真会话的实时对话——像 opencode 自己的 web 版，而不是 plannotator 插件
> 的消息机制。一期已开发的部分（悬浮球、管家界面、动效、`~/plannotator-butler/`）全部沿用。
> 一期原文：`doc/管家-数字总管-一期设计.md`（其 2.4 大脑与对话通道由本稿取代）。

## 1. 方向陈述

管家 = **一个常驻的真会话**（opencode 首发，Claude Code 后续），在总管文件夹里为主人工作。
Plannotator 页面（悬浮球 → 管家界面）是这个会话的**实时聊天界面**：

- 你在页面说的每句话，作为回合直接进入该会话（流式）；
- agent 的回复、工具调用、思考过程，像 opencode web 版一样实时渲染在对话流里；
- 同一个会话 id，终端里 `opencode -s <id>` 随时打开——**网页和终端是同一份对话**；
- **绕开 plannotator 插件机制**：无排队、无唤醒、无送达回执——管家是页面里的一等聊天公民，
  收件箱机制继续服务于其他普通 agent 与需求流程。

## 2. 目标与非目标

**目标（v3）**：管家会话跑在真引擎上；页面流式对话；persona 生效；历史跨重启延续；
终端互通；管家界面沿用一期视觉。

**非目标（本期不做）**：Claude Code 引擎（二期，Agent SDK 已在根依赖）；管家的需求操作与
派活（二期）；语音/数字人；多管家。

## 3. 架构（实现载体已存在：packages/ai/providers/opencode-sdk.ts，778 行）

```
管家界面（悬浮球 → 对话流 + 输入框）
   │ AIProvider/AISession 接口（createSession / 流式对话）
OpenCodeProvider（packages/ai/providers/opencode-sdk.ts）
   │  自起专用 opencode serve（dispose/进程退出时清理，一个进程共享本进程全部会话）
   │  SSE /event 流式（message.part.delta 增量）
   │  system 提示注入、会话创建/续接
opencode 服务（专用、随守护进程）
   │
管家会话（真会话：cwd=~/plannotator-butler/，终端 `opencode -s <id>` 同一对话流）
```

**实现载体今天核实在案**：该 provider 用 `@opencode-ai/sdk@1.19.3`（自带 patch）自起专用
serve、创建会话、SSE 流式渲染（`message.part.delta` 增量）、`buildSystemPrompt`（persona
注入点）、`withAskAiChildEnv`（Ask 通道子会话环境）——一期 2.4 说的「Ask 通道 AI 会话机制」
选它作为 provider 即可，管家的大脑天然就是真 opencode 会话。

## 4. 服务端代理层（大幅简化：服务生命周期 provider 已自管）

| 端点 | 说明 |

| `POST /api/inbox/butler/message` | `{ text }` → provider 会话 `prompt`（persona 经 provider 的 system 注入）；流式返回增量 |
| `GET /api/inbox/butler/history` | provider 会话消息映射为气泡结构 |

- ~~服务生命周期管理~~：provider 自起自清专用 serve（spawn/dispose/进程退出清理）。
- **认证**：SDK client 接管（1.19.3 带 patch）。
- **persona**：`buildSystemPrompt` + provider 的 system 通道。

## 5. 渲染映射（对话流 ← opencode 消息部件）

| opencode 部件 | 管家对话流 |
| --- | --- |
| text（流式增量） | 管家气泡流式渲染 |
| 工具调用/结果 | 折叠的状态行（图标 + 一句话，点开看详情） |
| 文件/图片部件 | 附件卡 |
| agent 回复的归属 | OpenCode · 管家（头像用管家徽标，不再有「某个 agent」问题） |

## 6. 与收件箱机制的关系

- 管家对话**不走**收件箱消息/队列/唤醒/送达回执——没有「未送达」语义，发出去就是进了会话。
- 收件箱与需求流程照旧服务普通 agent；管家要主动汇报/领活，二期给管家会话配
  `plannotator_inbox` 工具（归属已可写对：`PLANNOTATOR_SESSION_TAG=opencode:<管家会话>`）。

## 8. 验收（v3）

1. 守护进程启动后，管家专用 opencode 服务常驻（state.json 可查）。
2. 页面发消息 → opencode 终端 `opencode -s <管家会话>` 能看到原话作为回合出现。
3. 对话流流式渲染 agent 回复与工具状态；归属显示 OpenCode · 管家。
4. persona 生效（自称管家）；重启守护进程 → 会话与历史延续。
5. 收件箱发送通道不受影响（普通 agent 照旧）。

## 8.5、关键未解（2026-11-25 探针实测，下一轮第一件事）

**opencode 2.3.0 的 serve 不提供 HTTP 建会话**：SDK 1.19.3 的 `session.create`
（POST /session，带/不带 x-opencode-directory 均试）返回 405；POST /session_v2
同样 405；GET /session、/session_v2 正常（200）。SDK 客户端带 directory 配置
也 405——是 serve 构建真实不路由该方法，非请求形状问题。

含义：管家的「建会话」不能走 serve HTTP。候选路线（下一轮研究定夺）：
1. CLI 建会话一次（`run --session <新id> "初始化"`，已实测能建），之后用 serve
   的 `POST /session/{id}/message`（SDK SessionPrompt）驱动回合——该端点待验证；
2. 读 opencode 2.3.0 源码/文档，找到 serve 的会话创建端点（可能路径/方法不同）；
3. 管家自持 sqlite 写入（不推荐——绕过官方层）。

## 9. 风险与开放问题

- **服务生命周期**：standalone 服务的常驻/回收策略（空闲杀 vs 常驻）——倾向常驻（管家就该在）。
- **MCP shim 归属洞**：管家会话若配工具（二期），须先解 opencode 服务孵化 MCP 子进程的
  env 链（env 实锤见交接文档「四点五」）；一期纯对话不涉。
- **事件流断线**：SSE 断线重订的增量补偿（用消息 id 去重 + 全量历史兜底）。
- **模型与成本**：管家会话的模型沿用 opencode.json 的默认配置（主人可改）。
