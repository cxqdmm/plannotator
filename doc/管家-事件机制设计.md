# 管家事件机制设计方案（事件驱动 · 需求台账 · 动作分级）

> 定位：管家不是"能聊天的入口"，而是**收件箱的前台 + 调度台**。本方案定义它如何"知道情况、记住需求、盯住进展、在事件触发后行动"。
>
> 关键前提（owner 2026-11-26 纠正）：**MCP 是「干活的人 ↔ 收件箱」的执行面工具通道，管家不走 MCP**。管家有自己的观察面（事件流）与行动面（管家专用动作通道）。

---

## 一、背景与目标

现状：管家只有两个技能（需求受理、收件箱向导）+ 自由对话；对收件箱完全不可见——不知道有哪些需求、哪个会话在跑、什么在等人审。它只能"聊"，不能"当家"。

目标（本期）：让管家成为**需求项目的管理者**：

1. **记得需求**：每个需求的背景、约束、已定决策、相关会话与附件。
2. **记得进展**：语义化的进展时间线（不是原始消息堆）。
3. **知道事件**：收件箱发生的事（交付、裁决、会话状态、提问、失败）实时到达管家。
4. **会接动作**：事件触发后知道下一步该谁动、该不该叫人、该不该自己办。
5. **不漏事**：管家重启/掉线后从游标补课，事件不丢、不重。

一句话：需求 = 项目，事件 = 项目动态，台账 = 项目档案，规则 = 流程，管家 = 项目经理，人是审批人。

---

## 二、结论先行：三个面

| 面 | 谁和谁 | 载体 | 现状 |
|---|---|---|---|
| **执行面** | 执行会话 ↔ 收件箱 | MCP 工具（requirement / launch / inbox） | 已有，不动 |
| **观察面** | 收件箱 → 管家 | **事件流**（语义事件 + 游标） | 本期新建 |
| **行动面** | 管家 → 收件箱 | **管家动作通道**（建卡/派活/转达/催办） | 本期新建 |

三面互不复用工具协议：执行面是给干活的人用的，观察面是只读的，行动面是收件箱的内部能力（守护进程内部接口），**不为管家开放 MCP 工具**。

---

## 三、术语

- **原始事件**：收件箱里真实发生的一条事实（消息落下、阶段变更、会话失败）。
- **语义事件**：面向人/管家的一句话状态变化（"设计稿已交付，等你审""会话失败：额度耗尽"）。
- **事件游标**：管家已处理到的事件位置；重启后从这里续。
- **需求台账**：每个需求一份，包含背景、时间线、待办、下一步。
- **规则（playbook）**：事件 + 阶段 → 动作 的判定表。
- **动作分级**：L0 记录 / L1 提醒 / L2 低风险自动 / L3 派活（需授权）/ L4 替人拍板（不开放）。

---

## 四、事实源与投影（一致性模型）

- **收件箱是唯一事实源**：需求记录、历史事件、会话状态、消息全部在收件箱（daemon）里。
- **管家台账是投影 + 判断**：可丢弃、可重建；重建只需要一条游标与事实源。
- 铁律：**管家不得成为第二事实源**。它说的话必须能追溯到某条事件或某个需求字段；冲突时以收件箱为准。

这样避免"管家说一套、工坊显示一套"。

## 五、事件模型

### 5.1 事件信封

```ts
interface ButlerEvent {
  id: string;            // ULID，全局有序
  at: string;            // ISO 时间
  domain: 'requirement' | 'session' | 'thread' | 'system';
  kind: string;          // 见 5.2
  subject: {             // 这件事属于谁
    requirement?: string; // req_…
    thread?: string;      // msg_…
    session?: string;     // 会话 id
    launch?: string;      // lch_…
  };
  actor: 'person' | 'agent' | 'butler' | 'system';
  /** 语义化一行话（给管家与简报直接可用） */
  summary: string;
  /** 原始事实的引用：requirement 事件 id、消息 id、会话状态快照，供追溯 */
  ref?: { kind: string; id: string };
  /** 幂等键：同一事实重复到达只处理一次 */
  dedupe: string;
  /** 处理等级建议（规则可覆盖） */
  level: 'record' | 'notify' | 'act';
}
```

### 5.2 事件清单（本期）

**需求域**（来源：`requirement-events.json` 与 requirements 写入路径，已有）

| kind | 语义 | 备注 |
|---|---|---|
| `requirement.created` | 新需求：{标题} | actor=person/agent |
| `requirement.stage` | {需求} 阶段：{from} → {to} | 来自 progress 或手动 |
| `requirement.note` | 进展：{一句话} | progress 的 note |
| `requirement.delivered` | 交付：{提案/测试报告/评审}《{标题}》 | 带 thread 归属 |
| `requirement.verdict` | 审阅结论：已批准 / 已退回（附批注摘要） | 来自 审阅裁决 |
| `requirement.archived` | 需求归档 | |
| `requirement.context_added` | 需求补了上下文：{名称} | |
| `requirement.next_action_changed` | 台账派生的下一步变化 | 由投影产生 |

**会话域**（来源：bridge `state` 事件、launch run line、permission）

| kind | 语义 |
|---|---|
| `session.started` / `session.working` | 会话开始 / 工作中 |
| `session.waiting_person` | 会话在等主人回复（提问/权限） |
| `session.interrupted` | 一次打断已生效 / 被守卫拒绝（附原因） |
| `session.stopped` | 会话被停止 |
| `session.failed` | 会话失败（附原因） |
| `session.ended` | 会话端了（插件断线/进程退出） |

**沟通域**（来源：store 消息线）

| kind | 语义 |
|---|---|
| `thread.person_message` | 主人在 {线程} 发了消息 |
| `thread.agent_message` | {会话} 汇报了一条消息 |
| `thread.agent_question` | {会话} 在等主人回答 |

**系统域**

| kind | 语义 |
|---|---|
| `system.daemon_restart` | 守护进程重启（管家需要补课） |
| `system.plugin_offline` | 某个 agent 的插件离线 |

> 实施提示：不新增一套存储，**以收件箱现有事实为源做投影**——需求事件读 `requirement-events.json`（已有 append-only 日志），会话状态读 live sessions 的 state 事件，消息读 store 订阅线；系统域由守护进程自身发出。

### 5.3 语义化（原始 → 语义）

原始事件 ≠ 管家能直接用的话。示例规则：

- `deliverable(kind=design-doc)` 且该需求阶段=设计评审 且无裁决 → `requirement.delivered`，summary 写成「设计稿《X》已交付，等您审阅」。
- `say(field=审阅裁决, to=approved)` → `requirement.verdict`，summary「《X》已通过，进入需求开发」。
- `stage → done` → summary「需求已完成，可归档」。

语义化集中在一处（投影器），不散落在 UI 与管家两侧。

### 5.4 游标、回放、幂等

- 管家在 `~/plannotator-butler/events.cursor.json` 记录每个域的最后事件 id。
- 启动或重连：从游标之后回放；无游标则只从"现在"开始，并生成一条 `system.first_attach` 让管家知道"以前的事我不在"。
- 每条事件用 `dedupe` 幂等：重复投递只处理一次（处理记录放在台账里）。
- 保留期：事实源的日志保留期即回放上限；超出则明确告知管家"有缺口"，不得假装知道。

### 5.5 合并与去噪

- **同一需求** 60 秒内同域的多条事件合并成一条动态（例：一次会话连续 5 条进度只报最后一条 + 计数）。
- **同会话** 的状态抖动（busy→idle→busy）合并，只保留稳定态。
- 合并规则按域可配；合并后仍保留原始事件 id 列表供追溯。

## 六、需求台账（管家的记忆）

### 6.1 目录

```
~/plannotator-butler/
  ledger/
    <req_id>.md        # 人读：背景、决策、进展、待办（管家回答时读它）
    <req_id>.json      # 机读：结构化字段 + 事件游标 + 已处理 dedupe
  events.cursor.json   # 全局游标
  digest/              # 简报存档（可清理）
```

台账用 Markdown + JSON 双份：**模型读 md、程序读 json**，同一份事实两种视图。

### 6.2 台账字段

```ts
interface RequirementLedger {
  req: string;
  title: string;
  stage: string;
  background: {
    why: string | null;            // 为什么做（人说的）
    constraints: string[];         // 约束（人说的）
    decisions: { at: string; text: string; by: 'person'|'butler' }[];
    links: { kind: 'thread'|'deliverable'|'context'; ref: string; title?: string }[];
  };
  timeline: { at: string; summary: string; eventIds: string[] }[];
  todos: {
    on_person: string[];           // 等主人：审阅、拍板、回话
    on_session: string[];          // 等会话：在跑的事
    on_butler: string[];           // 等管家：该催、该转达、该补上下文
  };
  next_action: { text: string; why: string; level: 'record'|'notify'|'act'; at: string } | null;
  cursor: { lastEventId: string | null };
}
```

### 6.3 台账怎么更新

- **事件驱动**：每条语义事件 → 投影器 upsert 台账（确定性规则，不依赖模型）。
- **对话补充**：主人跟管家说的话（"这个先别做，等设计稿"）→ 管家写背景/决策（**要留痕**：记为 `actor=person` 的决策，不覆盖事实）。
- 管家不得改写进展时间线，只能追加。

### 6.4 待办三栏

- **等你**：需求待审阅、会话在等回复、需要拍板的分歧。
- **等会话**：正在跑的需求。
- **等管家**：该提醒的、该转达的、该补上下文的。

三栏是简报的唯一数据源——简报不现编。

## 七、规则与动作

### 7.1 规则表（事件 × 阶段 → 动作）

| 事件 | 条件 | 动作 | 等级 |
|---|---|---|---|
| `requirement.delivered` | kind=design-doc，无裁决 | 提醒「等你审阅」+ 给审阅入口 | L1 |
| `requirement.verdict` | approved | 记录 + 告知会话已进入开发；若需求下一步是派活，提示可开新会话 | L1 |
| `requirement.verdict` | annotated（退回） | 把批注摘要转达给产出会话（若还活着），否则提醒主人重开会话 | L1/L2 |
| `session.failed` | 有对应需求 | 记入台账 + 说明原因 + 给出可选下一步（重试/改配置） | L1 |
| `session.waiting_person` | — | 列入「等你」并提醒（合并同一会话的多次提问） | L1 |
| `thread.agent_question` | 需求在跑 | 提醒 + 摘一句问题原文 | L1 |
| `requirement.stage` → 设计评审 | 无设计稿 | 提醒产出会话补设计稿 | L1 |
| 主人说「这个先别做」 | 需求在跑 | 暂停：通知会话停止/打断，阶段记为暂停 | L3（首次授权后） |
| 需求新建且主人说「直接开」 | — | 建卡 + 派活 | L3（首次授权后） |

规则先以**代码内固定表**实现（M1/M2），M3 再支持主人用自然语言调整（"这类别来烦我"），调整写进管家偏好文件，需可查看、可撤销。

### 7.2 动作分级

| 级别 | 含义 | 例 | 默认 |
|---|---|---|---|
| L0 | 只记录，不打扰 | 会话进入工作中 | 开 |
| L1 | 提醒（合并进简报/线程） | 设计稿待审、会话失败 | 开 |
| L2 | 低风险自动办 + 报备 | 重试失败会话、把批注转达给会话 | 开（可关） |
| L3 | 派活/停止（需一次授权） | 建卡后直接开会话、暂停需求 | 关，首次询问后记住 |
| L4 | 替人拍板（审批结论） | 替主人通过设计稿 | **永久不开放** |

### 7.3 动作通道（行动面）

管家动作走守护进程内部接口（窗口/本机信任域），**不复用、不开放执行面的 MCP 工具**：

```
POST /api/inbox/butler/act
{ action: 'create-requirement' | 'launch-session' | 'tell-session' | 'stop-session' | 'remind', ... }
```

- 每个动作携带 `by: butler` 与触发它的 `eventId`，写进需求历史（归属可查）。
- 动作失败要回给管家（它能如实汇报，而不是假装做了）。
- 授权：L3 动作首次执行时向主人要一次确认，结果记进偏好文件。

### 7.4 审计

管家每一次动作都产生一条 **管家事件**（`actor=butler`），与人的操作同样进入需求历史。做到"它干了什么，台账里一目了然"。

## 八、管家与模型的交互

### 8.1 三种触发

1. **事件唤醒（被动）**：合并后的事件摘要作为一条系统消息进入管家会话："【动态】需求 X：设计稿已交付，等你审阅。下一步：提醒主人。"
2. **主人提问（主动）**：主人问"我那事怎么样了" → 管家读台账 md 回答，事实优先于记忆。
3. **定时简报（可选）**：每天固定时段一条"今天等你的事"，默认关闭，主人可开。

### 8.2 上下文预算

- 唤醒消息 **≤ 12 行**：只给语义摘要 + 需求 id；不给原始事件、不给全文。
- 需要细节时管家**按需读** `ledger/<id>.md`（最多 1–2 份），不把全量台账塞进上下文。
- 台账超过 60 条时间线时折叠为「最近 20 条 + 更早 N 条」摘要，避免膨胀。

### 8.3 防幻觉

- 回答涉及"事实"（谁交付了什么、什么阶段、谁在等）时，**必须**来自台账/事件；没有就说不确定。
- 引用时带需求 id 或事件 id，主人可回查工坊历史。

## 九、通知与人机界面

### 9.1 简报格式（示例）

```
今天等你 2 件
1) 「工坊改造」设计稿已交付 → 去审阅
2) 「小游戏」会话失败：额度耗尽 → 重试 / 换模型
在跑 1 件：「管家事件机制」需求开发中
```

- 只列"等你"和"失败"，不列正常推进的流水账。
- 一条简报最多 5 条，多的折叠成「还有 N 条」。

### 9.2 静默规则

- 同一需求的同类提醒 30 分钟内只一次。
- 主人正在该线程对话时不重复提醒。
- 夜间（可配置）只记录不提醒。

## 十、失败与恢复

| 情形 | 行为 |
|---|---|
| 守护进程重启 | 游标回放；补课后给一条"我回来了，期间有 N 条动态" |
| 管家会话挂起/断开 | 事件继续入日志；管家回来按游标补 |
| 事件重复投递 | `dedupe` 幂等，台账不重复记 |
| 事实源日志有缺口 | 明确说"这段我不在，可能有遗漏"，不编 |
| 需求被删除/归档 | 台账标 tombstone，保留只读，不再提醒 |
| 规则误判 | 主人能否决一次（"这条不用提醒"），记为偏好 |

---

## 十一、安全与隐私

- 事件与台账只在本机（管家文件夹，0600）。
- 事件摘要会进入模型上下文：**不包含**文件全文、代码全文、令牌；只给标题、状态、一句摘要。
- 附件只给路径与名称；需要内容时管家按需读取（可审计）。

---

## 十二、分期实施

**M1 观察面（先做，价值最高）**
- 语义事件投影器 + 游标 + 回放
- 需求台账（md + json）+ 事件驱动更新
- 只读简报：主人问"现在什么情况"能答对；事件唤醒推送摘要
- 验收：交付设计稿、会话失败、主人发消息三类事件，30 秒内到达；重启后不漏不重

**M2 行动面**
- 建卡、派活、转达、停止 四类动作 + 授权
- 动作写进需求历史（actor=butler）
- 验收：说"把 X 建卡并开工"→ 卡片出现、会话开跑、历史两条（建卡 + 启动）

**M3 规则可配 + 偏好记忆**
- 自然语言调整规则（"这类别来烦我"），偏好可查看/撤销
- 验收：改一条规则后，同类事件不再提醒

**M4 主动调度**
- 定时简报、自动重试、卡点催办
- 验收：无人干预下，一个卡住的需求被管家发现并给出下一步

## 十三、测试要点

- 投影器：每类原始事件 → 语义事件的确定性输出（表驱动）
- 游标：重启后只补新事件；缺口提示
- 幂等：同一事件投递 3 次只记 1 条
- 合并：60 秒内 5 条进度 → 1 条动态 + 计数
- 规则：交付→提醒；裁决通过→记录；失败→提醒；waiting_person→列入等你
- 动作：授权一次后 L3 不再问；未授权时只提醒
- 审计：动作产生 butler 事件并能回查
- 上下文：唤醒 ≤12 行；不把原始事件全文塞进模型

## 十四、待主人拍板

1. **台账归属**：同意"收件箱是唯一事实源，台账只是投影"吗？（否则会出现两套真相）
2. **事件粒度**：按本方案的语义事件（推荐），还是先给管家原始事件让它自己归纳？
3. **L2 自动办的范围**：失败重试、批注转达，这两项默认开启可以吗？
4. **简报节奏**：只在"等你"时出现（推荐），还是也给"在跑"的进度流水？
