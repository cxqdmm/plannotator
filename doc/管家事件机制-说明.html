管家不再只是
会聊天。

收件箱里的每一次交付、裁决、提问、失败和会话状态变化，现在都会变成一句人话， 进入每个需求的台账；需要主人时，管家会先开口。现在他也能动手： 建卡、派活、转达、停下——动作写进需求历史，派活和停止第一次要您点头。 他不是第二个事实源：台账只是收件箱的投影，随时可以从一条游标重建。

事件驱动 收件箱是唯一事实源 游标 · 可重放 幂等 · 合并 · 静默 执行面 MCP 零改动 M2 · 行动面
01 · 事实源 收件箱 需求日志 / 消息日志 / 会话状态
02 · 投影 语义事件 原始事实 → 一句状态变化
03 · 记忆 需求台账 进展 / 等你 / 等会话 / 下一步

01

它现在会做什么

从“只能聊”，到“知道情况、记得需求、盯得住进展、在需要时开口，需要时动手”。

01

记得需求

每个需求一份台账，人读的 .md 与机器读的 .json 同源：标题、阶段、背景链接、进展、等待关系、下一步。

ledger/<req_id>.md + .json
02

记得进展

不是原始消息堆：每条进展是一句状态变化；60 秒内同域的连续记录折叠成一条，并保留合并计数。

timeline · merged ×N
03

知道事件

三类事实源汇入：需求历史日志、收件箱消息日志、live 会话轮询；再加系统自身的首次接入与重启。

requirement · thread · session · system
04

不漏事

游标记录每个域读到哪里；重启只补漏掉的；全局 dedupe 让同一条事实只落一次；首次接入会明说“以前的事我不在”。

events.cursor.json · replay
05

会先开口

提醒级事件合并成 ≤12 行的 【动态】：主人已经开过管家会话时，管家会主动说一句；否则摘要等待下一次对话，随提问一起进入提示词。同一需求、同一类提醒 30 分钟内只响一次。

wake · digest · 30 min silence
06

也会动手（M2）

建卡、派活、转达、停止，走管家自己的动作通道。派活和停止第一次要主人确认一次（L3），之后记住；每个动作都以「管家: …」写进需求历史，台账里 actor=butler。

action channel · L3 grant · idempotency · audit
02

怎么实现的

观察面只读；行动面是管家自己的写入通道；执行面（MCP 工具）一行没动。

事实源

Inbox is the truth
  • requirement-events.json新建 / 阶段 / 交付 / 裁决 / 上下文 / 归档
  • store journal消息、问题；问题行带出询问的会话
  • live sessions每 5 秒比较一次开始 / 干活 / 结束
  • daemon itself首次接入、重启补课
→

投影器

deterministic projection
  • 语义化原始事件 → 人话 + 等级（record / notify / act）
  • 幂等id 与 dedupe 由事实派生，重复投递只算一次
  • 合并60 秒内同类记录折叠，保留 eventIds
  • 归属会话 / 线程 → 所属需求；链接不上就只记在事件流
  • 台账 upsert三栏待办 + 下一步，写 md 与 json
→

消费面

read-only, for the butler
  • 台账管家按需读 ledger/<id>.md，不塞全量进上下文
  • 简报GET /api/inbox/butler/brief（≤5 条，多的折叠）
  • 摘要唤醒 / 下一条提问前的【动态】，≤12 行
  • 页面管家页每 5 秒对齐历史，主动消息当场出现

铁律：管家不得成为第二事实源。每一条台账时间线都记着来源 event id；标题、阶段、归档标记在读取时以收件箱记录为准； 删除的需求留下只读 tombstone，不再提醒。冲突时，永远以收件箱为准。

为什么不给管家开 MCP 工具？ 执行面是「干活的人 ↔ 收件箱」的通道；观察面只读，行动面是管家自己的内部接口。 三面互不复用协议，才不会让管家的读取变成对执行会话的干扰。
行动面（M2，已建）：管家 → POST /api/inbox/butler/act → 建卡 / 派活 / 转达 / 停止。 它走的是与 New message、打断相同的写入路径；每个动作以「管家: …」进入需求历史（台账里 actor=butler）。 派活/停止（L3）第一次返回 needs_authorization，主人同意后带 authorized: true 重试，授权记在 preferences.json。
03

什么会变成事件

原始事件 ≠ 管家能用的话。投影器把事实收成一句可复述的状态变化，并建议处理等级。

kind语义（示例）域等级
requirement.delivered交付提案《登录页设计》，等主人裁决需求notify
requirement.verdict设计文档「登录页设计」被退回（批注 3 条）需求notify
requirement.stage《登录页改版》阶段：设计评审 → 需求开发需求notify record
requirement.note助手: 做完了登录页骨架需求record
session.failed助手 的会话失败：额度用完会话notify
session.waiting_person助手 在等主人批准一个操作：Bash会话notify
thread.agent_question助手 在等主人回答：用哪个配色？沟通notify
thread.person_message「登录页」里主人在说话沟通record
session.started / working / ended设计助手 开始了一个会话 / 在干活 / 结束了会话record
system.daemon_restart我回来了：期间有 5 条动态，已经补上系统record

}

语义化，集中在一处

projector

原始事实只描述“发生了什么”；投影器决定“这句话该怎么说、该不该叫人”。规则是确定性的，不依赖模型。

  • 设计稿交付且没有裁决 → 「等您审阅」，notify
  • 审阅裁决 = approved → 记录结论，会话可继续
  • 审阅裁决 = annotated → 「被退回」，等主人决定下一步
  • 会话失败 → 一句原因 + 下一步建议
  • 普通进展 / 会话开始 → 只记录，不打扰
04

台账长什么样

同一份事实，两种视图：模型读 Markdown，程序读 JSON。三栏待办是简报唯一的数据源。

暂无

可丢弃、可重建。台账不是数据库：删掉 ledger/ 也能从一条游标和收件箱事实重新投出来。 这就是“收件箱唯一事实源”的具体含义——管家说的话必须能追溯回某条事件或某个需求字段。
05

一致性、合并与安静

“不漏”和“不烦”是同一套机制的两端。以下数值都是代码里的常量，不是比喻。

Cursor

游标 + 补课

events.cursor.json 记需求日志位置、消息日志 seq、已投递时间与全局 dedupe。重启从游标之后回放，并说一句“我回来了，期间有 N 条动态”。首次接入则只从现在开始，并声明“以前的事我不在”。

Idempotency

同一条事实只落一次

事件 id 与 dedupe 都由事实派生：重放、重复投递、同一轮询的抖动都不会让台账长出第二条。dedupe 保留最近 500 条，跨重启生效。

60 s

合并，而不是刷屏

同一需求、同一域、60 秒内的记录级事实（进展、会话工作、会话汇报）折叠成一条，摘要取最后一条，带「合并 N 条」，原始 event id 全部保留。

30 min

同类提醒只响一次

同一需求、同一类 notify 事件 30 分钟内只提醒一次。提醒仍会记账，只是不再叫醒管家。事实不会因为安静而丢失。

≤ 12 lines

上下文预算

唤醒摘要最多 12 行，每条只给语义摘要和需求 id；细节留给 ledger/<id>.md 按需读取。台账时间线最多留 60 条，md 只显示最近 20 条。

Tombstone

删除的需求不再问

需求被删除后，台账保留为只读 tombstone：历史可回查，但待办清空、不再提醒。归档的需求同样退出简报。

阈值值作用
事件合并窗口60 s同需求同域的记录折叠
同类静默30 min同一需求同类提醒的间隔
会话轮询5 s开始 / 干活 / 结束的转换检测
唤醒防抖2 s一次事件潮只唤醒一次
简报条目≤ 5多出的折叠为「还有 N 条」
唤醒摘要≤ 12 行只给摘要 + 需求 id
台账时间线60 / 20JSON 保留 60 条，md 显示最近 20 条
dedupe 保留500跨重启的幂等窗口

07

怎么用

不需要新配置。重启一次 Inbox 守护进程，观察面和行动面就都在了。

打开管家，直接问

收件箱右下角的猫头鹰 → 管家页。问「现在什么情况？」「登录页那个需求怎么样了？」——人设要求它先读对应需求的台账，再回答。

#butler · 页面刷新不丢 · 每 5 秒对齐一次历史

什么都不用做，等它先说

设计稿交付、审阅退回、会话失败、会话提问、权限卡——这些提醒级事件会合并成一句「【动态】」。主人已经开过管家会话时，管家会主动说；否则摘要随下一次对话进入提示词。

同一需求同类提醒 30 分钟内只响一次。

让它动手

要建卡、派活、转达或停下时，管家走自己的动作通道（~/plannotator-butler/action.json 里的地址）。派活和停止第一次会先问您一次；同意后记住。

例：「把这个需求建卡，在 web 项目里开工」

查台账文件

所有台账在管家自己的文件夹里，人读的 Markdown 与机器读的 JSON 并列：

~/plannotator-butler/
  events.cursor.json        # 游标 / 已投递 / dedupe
  ledger/
    req_01J8….md            # 管家读这个
    req_01J8….json          # 程序读这个
  history.jsonl             # 管家对话历史

窗口内读简报与台账

两个只读接口，和管家路由一样只答同源窗口：

GET /api/inbox/butler/brief
GET /api/inbox/butler/ledger
GET /api/inbox/butler/ledger/<req_id>

从终端里读，带一个同源标记即可（本机信任域）：

curl -s -H 'sec-fetch-site: same-origin' \
  http://127.0.0.1:<port>/api/inbox/butler/brief

端口见 <dataDir>/inbox/inbox.json，或直接用当前 Inbox 的地址。

重启与沙箱

守护进程重启后从游标补课，不漏不重；首次接入只从现在开始，并明确告诉管家“以前的事我不在”。

测试与开发用 PLANNOTATOR_BUTLER_DIR 把管家文件夹指到临时目录，不会碰真实台账。

08

现在，他能动手了

M2 行动面：五个动作，一条只属于管家的写入通道。每一步都写进需求历史；派活和停止，第一次要您点头。

action做什么级别
create-requirement建一张需求卡，背景与要点一起落账L2
launch-session从需求卡开一个执行会话（项目或文件夹）L3
tell-session把一句话转达给正在干活的会话L2
stop-session让会话停下（打断下一次轮询送达）L3
remind在需求上留一句提醒，进台账L1

调用方式

butler's own curl

地址在管家文件夹的 action.json（每次启动重写）。管家从本机 curl 调用，窗口同源也可以；别的站点被拒。

cat ~/plannotator-butler/action.json
# { "url": "http://127.0.0.1:53998/api/inbox/butler/act", ... }

curl -s -X POST "$URL" \
  -H 'content-type: application/json' \
  -d '{"action":"create-requirement",
       "title":"登录页改版",
       "idempotency_key":"k-1"}'

每个动作带一个 idempotency_key；重试复用同一个，不会建出第二张卡、开第二个会话。

授权与审计

L3 · actor=butler
  • 派活 / 停止第一次返回 needs_authorization；管家先问您，同意后带 authorized: true 重试。
  • 授权按动作记在 ~/plannotator-butler/preferences.json，下次不再问；M3 会做成可查看、可撤销。
  • 动作成功以「管家: …」写进需求历史，台账显示 actor=butler；没有需求时记一条管家事件。
  • 失败原样回给管家：它只能如实汇报，不能假装做成。

您说：「把这个建卡，然后开工」

管家先问清项目或文件夹；它不猜。

create-requirement → 卡片出现

需求卡落在工坊；历史里多一行 管家: 替主人建了这张卡。

launch-session → 会话开跑

第一次返回 needs_authorization；您同意后重试。卡挂到新线程，历史里多一行 管家: 开好了执行会话。

验收：卡片、会话、两条历史

这正是设计文档 M2 的验收。一条集成测试用真实 Inbox + 假 agent 跑通了整条链路；重复的 idempotency key 不会多建卡或多开会话。

管家聊天不是线程。它自己的对话是管家文件夹里的真 opencode 会话；需求卡是工坊记录，执行会话从卡上开自己的线程。 这张卡不会自动落到聊天上——之前他说“您在哪儿开口，哪儿就是线程”是错的，人设已经写死了这条边界。

design §14
  • 收件箱是唯一事实源，台账只是投影。
  • 事件采用语义化粒度，而不是把原始事件丢给模型归纳。
  • 简报只列「等你」与失败，不列正常推进的流水账。
  • 行动面走守护进程内部接口，不开放 MCP；建卡、转达按 L2 直接办并留痕。
  • 派活、停止按 L3：第一次询问，授权记进偏好文件。

已知的诚实边界

limits
  • 没有游标时只从现在开始，不伪造历史。
  • 事实源日志若被截断，无法凭空知道缺口；台账只反映收件箱还在的事实。
  • 会话「结束」靠轮询检测，离线期间结束的会话不会产生事件。
  • 简报与台账路由目前只答同源窗口（本机信任域）。
  • L3 的确认是对话里的一次确认；授权在 preferences.json，删掉它即可重新询问（M3 做界面）。
  • 动作通道是本机信任域：无浏览器头的本机 curl 与窗口可调；别的站点被拒。
